# Security

ctx-gate installs local shell hooks (`.github/hooks/ctx-gate.json`) that
execute on every developer prompt inside repos that adopt it. Its
optional `codebase-memory-mcp` integration reads full source-tree
contents, though everything stays local: no network calls, no data
leaves the machine, no telemetry.

**Before company-wide rollout**, this tool — and specifically the
`.github/hooks/*.json` hook scripts and the `codebase-memory-mcp`
integration — should go through internal security review.

## What actually executes

- `ctx-gate check` / `learn` / `enforce` (`src/core/gate.js`,
  `learn.js`, `enforce.js`) are fully deterministic: regex, word lists,
  local file reads/writes, no LLM calls, no network calls. Everything
  reads from and writes to local files inside the target repo only.
- If a hook script errors, it fails silently from the developer's point
  of view: logs to `.context-ops/logs/ctx-gate.log`, exits 0. A broken
  gate must never block normal Copilot usage — verified in this repo's
  test suite by feeding it malformed input and confirming it still
  exits 0 with an empty response.
- `ctx-gate enforce` can `deny` a write-type tool call once a team opts
  into `block` level (off by default, changed only via a reviewed PR to
  `.context-ops/config.yml`, or a personal opt-in via
  `.context-ops/config.local.yml` that can only raise the level, never
  lower it).
- `install.ps1` / `install.sh` copy files onto the local machine
  (`~/.ctx-gate/<version>/` or the Windows equivalent) and run
  `ctx-gate init` in the invoking repo. No files are downloaded from the
  network by these scripts — they operate on a local clone of this repo.

## codebase-memory-mcp

`codebase-memory-mcp` is a third-party binary that reads the full source
tree to build a search index. ctx-gate:

- **Never installs it automatically, on any OS, at any point** (see
  `src/core/init.js` / `src/mcp/codebaseMemoryClient.js`). `ctx-gate
  init` only checks whether it's already on PATH and prints manual
  install instructions if it isn't. `ctx-gate init` can, with explicit
  `[y/N]` confirmation (a diff is shown first, same pattern as
  `mcp-trim`), write the `.vscode/mcp.json` *config entry* naming the
  server — this never fetches or runs the binary itself, which still
  requires the manual install above.
- Speaks to it only over local stdio JSON-RPC (`src/mcp/codebaseMemoryClient.js`)
  with a ~1.5s timeout that resolves to an empty result on any failure —
  never blocks, never crashes `ctx-gate check`.
- Falls back to a plain substring search over `git ls-files`
  (`src/mcp/textSearchFallback.js`) whenever the binary isn't present.
- Requires internal security approval before installing on a company
  machine, since it reads full repo contents (even though it stays
  local) — this is called out directly in the guidance text
  `ctx-gate init` prints when the binary is missing.

## Data handling

Every file ctx-gate reads or writes lives under `.context-ops/` inside
the target repo, or under the developer's own `~/.ctx-gate/` install
directory. Nothing is centralized across repos, nothing is sent to a
server ctx-gate controls, and nothing is sent to an LLM by the
Requirement Gate (the Context Optimizer's output is read by Copilot
itself, not generated by calling one).

Report suspected security issues to your internal security team per your
organization's standard process before this tool is used outside of a
trusted pilot repo.
